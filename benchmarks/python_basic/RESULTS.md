## 工具错误与验收修订

任务全通过与工具零错误是两回事。baseline 的 python-030 / repeat 2 中，Agent 尝试通过 shell 读取工作区内的 .pyc 文件，工具返回 UTF-8 解码错误；随后完成了代码修改并通过验收。工具层 subprocess 使用 text=True，二进制/非 UTF-8 输出需要更稳健的处理。该案例是已恢复的工具错误，不是任务失败。

candidate 的 python-002 / repeat 2 也出现了同类解码错误。python-027 / repeat 3 则调用了未注册的 `bash`，收到 `未知工具: bash` 后继续使用有效工具，并在后续调用 `run_bash`，最终通过验收。这为工具名约束与错误恢复提供了可复核案例，不能因任务最终通过而忽略过程错误。

pilot 阶段发现 python-022 的委托检查错误拒绝了合法的 from import 别名调用；验收已修正并增加两种合法委托及复制实现的回归检查，任务契约也明确允许这两种导入方式。旧试跑目录 prompt-test-contract-draft/ 完整保留，但不进入任何正式分母或差值。本文数据来自修订后重新冻结、完整执行的 90 个 attempt，系统提示词未因试跑结果调整。
该 test 集经历了验收质量修订，因此不能称为严格盲测；后续泛化结论应另建未参与开发的新任务集。

## 结论边界

这是单次、小型、人工任务集上的描述性结果。两侧均全通过，任务集出现成绩饱和；本次没有观察到 candidate 的成功率优势，其平均工具次数约增加 9.8%，平均耗时约增加 30.4%。这些是点估计，不能据此断言候选提示词在一般任务中更差。
15 个 test 任务和 3 次重复不足以推断普遍优势；顺序执行、采样波动和服务漂移也可能影响比较。下一轮需要另建更复杂、未参与开发的 held-out 任务，并预先确定评价标准。
模型 ID 是请求中的服务别名，未验证服务端实际模型快照。时延包含网络、工具和验收；本文未进行显著性检验或因果推断。
token/cost 仍未采集，费用不能从工具次数估算。任务级总时限未实施；只有请求与验收子进程超时。工具和安全计数部分来自字符串规则，零越界不等于安全证明。
